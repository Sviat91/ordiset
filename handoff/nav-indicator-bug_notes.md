# Nav-индикатор: незакрытый баг, требует planner (FULL mode)

## Статус
Пользователь остановил дальнейшие точечные фиксы после 8 раундов (`handoff/ordiset-nav-widget-fixes_plan.md` … `-8_plan.md` + соответствующие `_feedback.md`). Просил в следующий раз вызвать **planner**-агента (FULL mode), а не продолжать LIGHT-режим точечных правок.

## Симптом (последняя, самая точная формулировка пользователя)
- **С открытым DevTools**: индикатор работает идеально — и по клику, и по скроллу, в обе стороны, в любых сценариях.
- **С закрытым DevTools**:
  - Скролл колесом/трекпадом вообще не двигает индикатор (ни вперёд, ни назад) — воспроизводится стабильно, дважды подтверждено.
  - Клик по вкладке, соседней с текущей (шаг за шагом), работает нормально.
  - Клик "через несколько вкладок" (например, Overview → сразу на Notifications, минуя Customize/Mobile/Booking site) — линия СНАЧАЛА корректно переходит на Notifications, но затем **возвращается назад** ("на уровень ручи", предположительно на какую-то промежуточную секцию) и остаётся там — "живёт своей жизнью".

## Что уже пробовали (хронология, всё под lint/build "чисто" и с независимым код-ревью на каждом шаге)
1. Индикатора не было вообще → добавлен (IntersectionObserver, `rootMargin: -50%/-50%` "линия по центру экрана").
2. Клик по ссылке не скроллил назад к Overview → `scrollIntoView` → не помогло.
3. → `getBoundingClientRect().top + window.scrollY` → не помогло (подозрение: `transform: scale` от Framer Motion в `StackSection` портит `getBoundingClientRect`).
4. → `offsetTop`/`offsetParent`-цепочка → не помогло (тот же класс сомнений: неясно, стабилен ли `offsetTop` под `position: sticky`).
5. → сумма `offsetHeight` предыдущих секций (`getSectionTop`, НЕ читает позицию самой цели вообще) — **этот механизм скролла подтверждён пользователем как рабочий** и с тех пор не менялся, не трогать.
6. Индикатор не успевал синхронизироваться именно при клике (кликаешь Overview, линия остаётся на Notifications) → добавлен оптимистичный `setActiveId(id)` в момент клика + `suppressObserverRef`, подавляющий обновления от источника скролл-трекинга на время программного скролла, снимается по `scrollend` + `setTimeout(1000ms)`-подстраховка. **Клики (пошагово) с тех пор работают** — не трогать этот механизм подавления как таковой.
7. Индикатор при обычном скролле шёл только вперёд, назад — нет → диагностирован как ordering-bias в цикле по `entries` IntersectionObserver'а (последний в фиксированном порядке `SECTION_IDS` побеждал) → заменено на `computeActiveId()`: при каждом срабатывании честно пересчитывает, какая секция ближе всего к центру экрана по `getBoundingClientRect()`, без привязки к порядку. Направленная асимметрия при клике исчезла.
8. Индикатор вообще не двигался при обычном скролле (ни вперёд, ни назад), но ТОЛЬКО когда DevTools закрыт → заменили `IntersectionObserver` на самодельный `window.addEventListener("scroll")` + `requestAnimationFrame`-throttle → **не помогло**, тот же симптом (DevTools open работает, closed — нет).
9. → заменили самодельный scroll-listener на встроенный Framer Motion `useScroll()` + `useMotionValueEvent(scrollY, "change", ...)`, на основании того, что `StackSection.tsx` уже использует `useScroll` для scale-анимации карточек и НИ РАЗУ не давал сбоев за всю сессию (ни с открытым, ни с закрытым DevTools). Ревьюер прошёл по исходникам `framer-motion`/`motion-dom` и подтвердил, что `useScroll()` без `target` регистрируется на тот же самый `window`-скролл-листенер (`container = document.scrollingElement` по умолчанию), что и `StackSection`'ы. **Тем не менее — тот же симптом остался**: с закрытым DevTools скролл по-прежнему не двигает индикатор.

## Новая информация из последнего сообщения пользователя (ещё не исследована)
Раньше клик по СОСЕДНЕЙ вкладке (шаг за шагом) считался полностью надёжным, "не трогать". Теперь выяснилось: клик "через несколько вкладок сразу" (Overview → Notifications, пропуская 3 секции) с закрытым DevTools показывает временный скачок к правильной цели, а затем **возврат к неверному состоянию**. Это ПЕРВЫЙ раз, когда путь клика (не только путь скролла) тоже показал сбой с закрытым DevTools — и это важно, потому что путь клика ранее считался полностью надёжным и не менялся с раунда 6.

### Рабочая гипотеза (НЕ проверена, НЕ реализована — для planner'а)
`scrollToId` ставит `suppressObserverRef.current = true`, затем `setActiveId(id)` (оптимистично), затем запускает `window.scrollTo({ behavior: "smooth" })`, и снимает подавление либо по событию `scrollend`, либо через фиксированный `setTimeout(..., 1000)` — что раньше сработает. Для ДЛИННОГО прыжка (через несколько секций) реальная длительность плавной прокрутки браузера может ПРЕВЫШАТЬ 1000ms, и/или `scrollend` может сработать РАНЬШЕ фактического завершения анимации при определённых условиях (в частности — возможно по-разному в зависимости от того, открыт ли DevTools, если он влияет на частоту кадров/CPU-throttling браузера). Если подавление снимается ДО того, как скролл реально долетел до цели, `useMotionValueEvent`'s колбэк (уже разблокированный) поймает ПРОМЕЖУТОЧНУЮ, а не финальную секцию, и перезапишет корректный оптимистичный `activeId` неверным значением — что ровно соответствует описанному "сначала долетает до Notifications корректно, потом откатывается назад".

Это ещё не проверено и не реализовано — гипотеза для planner'а, не для слепого фикса. Если планер будет исследовать эту гипотезу, стоит рассмотреть: убрать фиксированный `setTimeout` fallback полностью и полагаться только на `scrollend` (менее надёжно на очень старых браузерах, но убирает риск преждевременного снятия подавления), либо привязать длительность fallback к реальной дистанции скролла, либо (возможно самое надёжное) не снимать подавление вообще до тех пор, пока `computeActiveId()` при следующем вызове не совпадёт с `id`, на который кликнули.

## Что НЕ трогать без необходимости (подтверждено рабочим, несколько раз перепроверено)
- `getSectionTop` / механизм вычисления цели скролла — работает.
- Структура клика (`scrollToId`, оптимистичный `setActiveId`) — работала для одиночных/соседних переходов вплоть до этого сообщения; возможно теперь тоже требует правки по гипотезе выше.
- `computeActiveId` (геометрический расчёт "ближайшая к центру секция") — логика подтверждена дважды независимым ревью, сомнений в ней самой нет.
- Ширина/переиспользование виджетов Overview/Customize — эта часть (раунд 5/6) подтверждена пользователем как решённая, к ней жалоб не было.
