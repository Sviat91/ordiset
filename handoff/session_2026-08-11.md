## Decisions Made
- **Stack**: Next.js (App Router, `next build`/`next start`) + TypeScript + Framer Motion + plain CSS Modules, deployed as a normal Node process via PM2 on the user's existing VPS — decided with the user, no Tailwind/UI kit/GSAP.
- **Scroll architecture**: pure CSS `position: sticky` + ascending z-index stacking, chosen over both the original pin/fade mechanic and a JS-heavy scroll-jacking approach — simpler, structurally avoids two real bug classes hit during the session (whileInView + scroll-linked style combined on one element; forced-height + centered content overflow), and matches the client's reference sites with less code.
- **`overflow-x: clip` not `hidden`** on `html`/`body` — required for `position: sticky` to work at all; `clip` avoids the CSS spec's "non-visible axis forces the other axis to auto" coercion that `hidden` triggers.
- **No browser automation this session** — explicit, emphatic user instruction ("прекрати запускать браузер, это запрещено все"). All subsequent verification relied on `npm run lint`/`build`, `sips`/raw PNG pixel decoding, and manual CSS/layout arithmetic instead.
- **Section order**: Hero, Customize, Mobile, Booking site, Notifications, Contact — confirmed explicitly via AskUserQuestion rather than assumed, since the client's verbal description only mentioned 3 of the 6 widgets by name.
- **Agent orchestration**: followed the user's CLAUDE.md FULL-mode flow (planner → coder → reviewer, sequential, file-based handoff) for both the initial build and the redesign; used SINGLE mode (direct edits, no agents) for small well-defined fixes (accent color swap, focus-ring fix, `.centerY` fix). Planner's configured model (`claude-opus-5`) was unavailable in this environment — used `opus` override instead both times.
