# Session: 2026-08-24

## Completed
- **i18n round 1 — full EN/UK/PL rollout** (`handoff/i18n_plan.md` / `_feedback.md`, LIGHT→FULL mode, planner→coder→reviewer, APPROVED): moved the site under `app/[lang]/`, added `proxy.ts` for `Accept-Language`-based locale detection/redirect (`/` → `/en|uk|pl`), created `dictionaries/{en,uk,pl}.json` with genuine Ukrainian/Polish marketing translations (not machine-literal), and wired every text-bearing component (`Nav`, `Hero`, `ContactForm`, all 6 sections) to read from them. Added a first-pass 3-button `EN/UA/PL` switcher in `Nav.tsx`. Locale-aware metadata (`title`/OG/`hreflang`/`canonical`/`og:locale`) via `generateMetadata`. `autoClickText="View admin demo"` in `AdminPanelSection.tsx` deliberately kept hardcoded English — it's a DOM text matcher against the out-of-scope `demo-widget` iframe, not display copy. `npx tsc --noEmit` / `npm run build` clean; `/en /uk /pl` statically generated.
- **Diagnosed two real regressions via live `agent-browser` testing** (network capture + DOM probes against the running dev server — not guesswork, the user had already rejected one CSS-only guess earlier this session):
  1. Nav items visibly wrapped to 2 lines on longer UK/PL translations (measured: 34px vs 17px link height).
  2. **Major**: every locale switch fully reloaded all 5 embedded demo `<iframe>`s — HAR capture showed 92 requests per switch, including 5 `GET /demo-app/index.html` document reloads, even though the outer page itself never did a hard browser reload. Root cause: `[lang]` is the outermost route segment (per Next's own recommended i18n pattern), so `router.push` between locales has no stable React-tree ancestor to preserve identity against — the entire tree, including mounted iframes, gets torn down and rebuilt from a fresh RSC payload.
- **i18n round 2 — client-side locale context, no more remount** (`handoff/i18n_no_remount_plan.md` / `_feedback.md`, FULL mode, planner→coder→reviewer, APPROVED): moved locale/dictionary access to a new client `LocaleProvider`/`useLocale()` React Context (`components/LocaleProvider.tsx`, `lib/dictionaries-client.ts`). Switching locale is now `window.history.replaceState` (never `router.push`) — a pure in-place React state update, so nothing in the tree unmounts. All 9 text-bearing components (not just the 6 with iframes — `Nav`/`Hero`/`ContactForm` would otherwise have gone stale on a context-only switch) converted from server-fetched/prop-drilled dictionaries to `useLocale()`. `Dictionary` type relocated to `lib/locales.ts` to avoid a `next/root-params` import hazard in Client Components. Also in this round: shortened the long UK/PL nav labels, added `white-space: nowrap` as a wrap safety net (which forced moving the nav's "hide links" breakpoint from 768px to 1024px — a deliberate, math-justified consequence, flagged to the user but not yet explicitly signed off on), rewrote the switcher as a `<details>/<summary>` dropdown, and fixed a stale nav-indicator bug (it only recomputed on scroll/resize, not on locale change).
  - **Independently verified live by the orchestrator** (not just trusted from the coder/reviewer reports): HAR capture of a real switch now shows **0 requests** (down from 92); markers on all 5 `iframe.contentWindow`s survive the switch; hydration-clean console on fresh loads of all 3 locales; scroll position preserved through a mid-page switch; admin-demo iframe still auto-navigates (`autoClickText` matcher intact) after two consecutive switches.

## User rejected two things after testing the live result tonight — both queued, not started
The user tested the shipped state right before ending the session and was unhappy with two things (their words, paraphrased for the record — they were emphatic and profane about it):
1. **The new `<details>/<summary>` language-switcher dropdown looks bad.** They want it visually redesigned into something that "opens beautifully" — the underlying mechanism (native `<details>`, keyboard/outside-click handling, real `<a href>`s) is functionally correct per round 2's testing and does **not** need to change, only its visual design (`components/LanguageSwitcher.module.css`). Likely needs the `frontend-design` skill given this project's design bar.
2. **The layout still visibly shifts/jumps when switching language — the original complaint is not fully resolved.** Round 2 fixed the iframe-remount symptom, but a *separate* root cause is still live: translated text naturally differs in height across EN/UK/PL (e.g. a heading wraps to a different number of lines per language), and several sections couple surrounding content's position to that text height — confirmed earlier this session for `MobileSection` specifically (`.split` CSS grid with `align-items: center`; measured ~25px vertical shift of the phone-frame between `/en` and `/uk`, driven by the 2-line vs 3-line heading). **Not yet audited**: whether the same failure mode exists in `Hero.tsx`, `BookingSiteSection.tsx`, `NotificationsSection.tsx`, `PreviewSection.tsx`, `AdminPanelSection.tsx` — only `MobileSection` was actually measured. User's explicit requirement: reserve container/section sizing based on the **maximum** content across all 3 locales, so switching language never resizes or moves anything outside the text block itself — no font-size tricks, no per-language sizing. Their own words: "должны быть заданы максимальные размеры контейнера под максимальный текст... шрифт внутри не должен трогаться."

The user explicitly said if I don't understand the layout-shift problem myself, run the planner to get it explained — meaning next session should likely open with a planner-led investigation across all 6 sections (not just MobileSection) before any coding starts.

## Decisions Made
- **Client-side locale Context over server-driven per-route dictionary fetching**, specifically because the embedded demo iframes must never remount on a language switch — this was proven with a live network capture showing the concrete regression (92 requests → 0), not decided from theory. See `handoff/i18n_no_remount_plan.md` D1–D3.
- **Live `agent-browser` testing (network capture + DOM/marker probes) proved decisive twice this session** for catching regressions that `tsc`/`npm run build`/static review could not see at all (both are green in both the broken and fixed states). Establish this as the standard verification step for any future "something feels visually/behaviorally off" report on this project — build-green is necessary but was clearly not sufficient here.
- **Nav "hide links" breakpoint moved from 768px to 1024px** as a deliberate, arithmetic-justified tradeoff (`white-space: nowrap` forces it once labels can't wrap) — communicated to the user in the same message that reported the fix, but they have not yet reacted to this specific point one way or the other. Worth confirming it reads fine to them, separate from the two items they did react to.
