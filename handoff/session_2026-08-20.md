## Decisions Made

- **Root-caused, then abandoned, native CSS `scroll-snap` entirely — replaced with a JS settle-dock.** Two rounds of CSS-only tuning (`mandatory`, then `proximity`) each shipped with a distinct new failure (jitter, then a severe up/down asymmetry). A dispatched planner found the actual mechanism: `.card` is `position:sticky`, so once scrolled past, it stays pinned at the viewport top for the rest of the page — meaning its `scroll-snap-align` candidate degenerates to "wherever you already are," which structurally can never provide a backward snap target. No CSS property (`scroll-margin`, `scroll-padding`, alternate `scroll-snap-align` values) can fix this — it's a selection-policy problem CSS scroll-snap doesn't expose controls for. Full write-up and 11/11-data-point validation in `handoff/scroll-snap-v2_plan.md`.
- **The plan's own JS-dock design (D6) had a real, previously-unconsidered race**, found only by live testing, not by the planner's static analysis: sampling `window.scrollY` inside the arm-time (`wheel`/`touch`) event handler is unsafe under `{passive:true}` listeners, since the browser may apply the scroll before the handler runs — this made the first coder-implemented version never dock at all, in either direction. Fixed directly by the orchestrator (not re-routed through planner/coder, since the fix was narrow and fully diagnosed) by tracking a `restYRef` written only inside `settle()`, never sampled from an input handler.
- **`restYRef` needed a second fix** to stay in sync after *completed* programmatic scrolls (Nav/Hero clicks) that never touch the dock — otherwise the next real gesture would compute against a stale baseline. Fixed by having every settle (armed or not) update `restYRef`, while only an armed settle evaluates a correction. (This is the mechanism the reviewer's remaining open finding is about — it covers the *completed*-scroll case but not the *interrupted-mid-flight* case.)
- **Nav auto-hide-on-Preview reverted** — explicit user feedback: enough room, keep the nav visible everywhere.
- **Extracted `lib/sections.ts`** (from `Nav.tsx`) as the single source of truth for section boundaries — used by `Nav.tsx`, `Hero.tsx`, and now `ScrollDock.tsx`. `getSectionTops()` deliberately stays on `el.offsetHeight` (transform-immune) — switching to `getBoundingClientRect()` would return scaled heights mid-animation and reintroduce boundary drift.
